# Single-parent delegated ticket workflow

The pilot has two independently keyed agent roles:

- `agent:ticket-pilot`: the primary agent, which can request a child grant from its own active root task.
- `agent:diagnostic`: a child agent, which can invoke tools only under grants issued to it.

Keys are provisioned by the host. Delegation passes authority, not a credential: the API does not mint or return the child's secret. Give a child runtime only `child.key`; never give it the primary, operator, or tool key.

## Automated scenario

With the Docker pilot running:

```sh
scopedact-pilot evaluate-delegation --output pilot-results/delegation-evaluation.json
```

The 19 checks cover assigned read; denied update and other-ticket read; denied parent-grant use; rejected privilege/resource/lifetime expansion; denied child approval and further delegation; parent pause/resume; later-step revocation; denied delegation after revocation; full lineage; and event-chain integrity.

This is a deterministic scripted workflow using distinct authenticated clients. It does not test live-model reasoning.

## Manual parent/child workflow

First create a root task as operator:

```sh
scopedact-pilot create-task --resource ticket:T-100
PARENT_TASK='COPY_RETURNED_TASK_ID'
```

As the primary agent, request a read-only grant for the configured child:

```sh
scopedact-pilot delegate --task-id "$PARENT_TASK" --resource ticket:T-100 --actions read --lifetime-seconds 300
CHILD_TASK='COPY_RETURNED_CHILD_TASK_ID'
```

As the child, read the assigned ticket and then try an unassigned ticket:

```sh
scopedact-pilot invoke --role child --task-id "$CHILD_TASK" --action read --resource ticket:T-100
scopedact-pilot invoke --role child --task-id "$CHILD_TASK" --action read --resource ticket:T-200
scopedact-pilot invoke --role child --task-id "$CHILD_TASK" --action update --resource ticket:T-100 --input-json '{"text":"Unauthorized update","expected_version":1}'
```

The first request executes. The next two are denied without dispatch, regardless of the update's expected version. Child authority cannot expand because the tool would otherwise accept a change.

Intervene during the workflow:

```sh
scopedact-pilot control --task-id "$PARENT_TASK" --operation revoke
scopedact-pilot invoke --role child --task-id "$CHILD_TASK" --action read --resource ticket:T-100
scopedact-pilot lineage --task-id "$PARENT_TASK"
```

The subsequent read is denied. The operator-only lineage command displays the initiator, parent, child, stored permissions, authenticated requesting actor, tool, reason code, and outcome. `--json` provides timestamps, request IDs, grant/task links, and delegation IDs. Attribution excludes proposal text from the exported lineage.

## Enforcement details

- Only the authenticated primary may delegate its own active root grant.
- Requested child permission pairs must be a nonempty subset of the parent.
- Child expiry cannot exceed parent expiry. Lifetimes are not silently widened or capped; invalid requests are rejected.
- Initiator is preserved. Child task ID and delegation ID are generated by the gateway.
- Grant, child task, and issuance event commit in one database transaction.
- Authenticated caller identity and stored grants supply lineage; callers cannot provide their own parent labels.
- Child invocations recheck their own grant, ancestor grant revocation/expiry, and ancestor lifecycle status. Parent pause blocks otherwise-allowed child actions; resume restores valid authority.
- One child hop is exposed by the pilot. Child-created delegation is rejected. No multi-parent or advanced graph mechanism is implemented.
- If a primary intentionally delegates update authority that it owns, the child still requires the same exact-content operator approval. The reference scenario deliberately delegates only read.

## Upgrade from v0.13

Stop old services and back up their state before upgrading. Keep existing primary/operator/tool keys. Run:

```sh
scopedact-pilot init-child
docker compose -f compose.pilot.yaml up --build -d --wait
```

`init-child` only creates a missing child key and refuses to overwrite it. No grant schema migration is needed; parent links and delegation IDs already existed. Old events remain intact but are not retroactively converted into the new attributed-action format. Use newly created tasks for a complete delegation report.

For a fresh review environment, use `init` instead; it creates four separate keys. Never commit these keys. Docker mounts the child key into the gateway and child probe only, not into the primary probe.
